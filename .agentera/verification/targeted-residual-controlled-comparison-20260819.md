## Method

The baseline and candidate used the same generated bytes and metadata for each retained matrix case. Baseline bypassed the pipeline. The candidate used the shipped built-in registry and `Runner`, restricted to explicit successful `read` results. For each lossy result, the original was first persisted in an isolated in-memory database under a deterministic valid 16-character source ID. The production footer was then built with that ID. The evaluator parsed the ID from the emitted `ktx read` cue, asserted it equaled the persisted ID, and passed the parsed ID to the shipped `GetSourceOutput` recovery path. Recovered bytes matched the original.

Latency policy was fixed before the retained run: 100 warmups followed by 1,000 paired samples per case, alternating arm order in one process and environment, using Go's monotonic elapsed clock. The operational gate was candidate mean below 2,000,000 ns for every case. The receipt retains count, sum, minimum, maximum, and integer mean, sufficient to regenerate the reported summaries. These are descriptive local measurements, not inferential or model evidence.

Tool-call effect is mechanical: pipeline execution introduced zero agent/runtime tool calls. The two lossy results each exercised one local retained-original retrieval; those recovery exercises are not agent/model calls.
