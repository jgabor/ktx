# Binary compatibility identity

`ktx binary-capabilities` is a DB-free diagnostic command. It identifies the
executable that handled the command without resolving or opening a database:

```json
{
  "schema": "ktx.binary-capabilities/v1",
  "executable_path": "/absolute/canonical/path/to/ktx",
  "executable_sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "build_version": "0.1.0-dev",
  "max_database_schema": 8
}
```

`executable_path` resolves symlinks. `executable_sha256` hashes the bytes at that
canonical path. `build_version` is embedded at build time, and
`max_database_schema` comes from the database schema owner without inspecting a
database.

This identity does not authorize database access. Query safety comes from
read-only SQLite access, and write safety comes from forward schema checks and
transactional migration. The identity remains useful for release verification,
support diagnostics, benchmark provenance, and newer-schema errors.

## Artifact comparison

`--expect-sha256` compares an independently supplied digest with the executable
without touching a database:

```sh
digest=$(sha256sum ./build/ktx | cut -d ' ' -f 1)
./build/ktx binary-capabilities --expect-sha256 "$digest"
```

A match exits `0` and adds:

```json
"comparison": {
  "expected_sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "status": "equal"
}
```

A mismatch exits `3` with the expected and actual digests and canonical path. A
malformed expected digest exits `1`. If the executable path or bytes cannot be
resolved and read, identity is unverifiable and the command exits `4`. None of
these paths opens a database.

## Schema diagnostics

When a database is newer than the running binary, the automatic
`schema-incompatible` error includes executable path, digest, build version, and
maximum schema. Those fields identify the binary that rejected the database;
the caller does not need to provide them. Recovery is forward-only: install a
binary supporting the actual schema or newer and retry. Never lower
`PRAGMA user_version`.

## OpenCode candidate pinning

The plugin generated by `ktx init opencode` resolves one `ktx` candidate when
its factory starts, canonicalizes the path, hashes its bytes, and queries that
exact path for `binary-capabilities`. It registers hooks only when the response
schema, path, digest, build version, and maximum schema match the observed
candidate. Every later callback uses the pinned absolute path, so a later
`PATH` change cannot select another executable.

Candidate path, digest, callback queue, and schema-error containment belong to
that factory instance. Re-run `ktx init opencode` and restart OpenCode after
replacing ktx so the generated integration and pinned identity are refreshed.
